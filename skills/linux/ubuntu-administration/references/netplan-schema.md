# Netplan YAML Reference

Netplan is a YAML abstraction layer that renders into either
`systemd-networkd` or `NetworkManager` configuration. It does not configure
the network itself — `netplan apply` (or `generate` + a renderer reload)
does.

## Top-level structure

```yaml
network:
  version: 2
  renderer: networkd        # or: NetworkManager
  ethernets: {}
  wifis: {}
  bonds: {}
  bridges: {}
  vlans: {}
```

`renderer:` at the top level sets the default; each device type can override
it individually. Desktop Ubuntu defaults to `NetworkManager`; server images
default to `networkd`.

## DHCP

```yaml
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: true
      dhcp6: false
      dhcp4-overrides:
        use-dns: false          # ignore DNS servers offered by DHCP
        use-routes: true
```

## Static addressing

```yaml
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: false
      addresses:
        - 192.168.1.10/24
        - 2001:db8::10/64        # multiple, including mixed v4/v6
      routes:
        - to: default
          via: 192.168.1.1
        - to: 10.0.0.0/8
          via: 192.168.1.254
          metric: 100
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8]
        search: [example.com]
```

`to: default` is the modern spelling for a default route; older examples use
`0.0.0.0/0`, which still works but `default` is clearer.

## Matching by MAC instead of interface name

Interface names vary across boots on some hardware/hypervisors. Match by MAC
and give it a stable name:

```yaml
network:
  version: 2
  ethernets:
    lan0:
      match:
        macaddress: "52:54:00:12:34:56"
      set-name: lan0
      dhcp4: true
```

## Bonding

```yaml
network:
  version: 2
  ethernets:
    eth0: {}
    eth1: {}
  bonds:
    bond0:
      interfaces: [eth0, eth1]
      addresses: [10.0.0.5/24]
      parameters:
        mode: 802.3ad
        lacp-rate: fast
        mii-monitor-interval: 100
```

## VLANs

```yaml
network:
  version: 2
  ethernets:
    eth0: {}
  vlans:
    vlan100:
      id: 100
      link: eth0
      addresses: [10.100.0.5/24]
```

## Bridges

```yaml
network:
  version: 2
  ethernets:
    eth0: {}
  bridges:
    br0:
      interfaces: [eth0]
      addresses: [10.0.0.5/24]
      parameters:
        stp: true
        forward-delay: 4
```

## Multiple interfaces, one config

```yaml
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: true
    eth1:
      dhcp4: false
      addresses: [192.168.50.1/24]
```

Each top-level device key is independent — combine DHCP and static in the
same file freely.

## Route policies (policy routing)

```yaml
network:
  version: 2
  ethernets:
    eth0:
      addresses: [10.0.0.5/24]
      routes:
        - to: 0.0.0.0/0
          via: 10.0.0.1
          table: 100
      routing-policy:
        - from: 10.0.0.5/32
          table: 100
```

For routing multiple uplinks with source-based selection — a common need on
multi-homed hosts.

## The rendering pipeline

```bash
netplan generate      # YAML -> backend config (systemd-networkd or NM), no reload
netplan apply          # generate + reload the renderer + reconfigure interfaces
netplan try            # apply + auto-revert after 120s unless confirmed
netplan status          # current live state, per interface
netplan get             # dump the merged configuration as YAML
netplan get ethernets.eth0.addresses
```

`generate` alone is the safe way to syntax-check a file — it writes to
`/run/systemd/network/` (or NetworkManager's config) without touching live
interfaces.

```bash
# Inspect what was actually generated, for the networkd renderer.
cat /run/systemd/network/10-netplan-*.network
```

## File permissions

Netplan **warns** — it does not refuse — when a config file under
`/etc/netplan/` is readable by group or other, because it may embed a WiFi
PSK:

```
** WARNING **: Permissions for /etc/netplan/01-netcfg.yaml are too open.
```

The configuration is still generated and applied. Silence the warning (and
follow the actual security intent) with:

```bash
chmod 600 /etc/netplan/*.yaml
```

If a Netplan change genuinely appears to do nothing, the cause is virtually
never this warning — check the generated backend file and `netplan status`
instead.

## File precedence

Files in `/etc/netplan/` are processed in lexical filename order and merged;
a later file's keys override an earlier file's for the same device.
Ubuntu's convention:

| Prefix | Purpose |
| --- | --- |
| `00-` | Installer/cloud-init defaults |
| `01-` to `49-` | Local admin overrides |
| `50-cloud-init.yaml` | Written by cloud-init on first boot |
| `90-` to `99-` | Late overrides, highest precedence |

Editing `50-cloud-init.yaml` directly is fragile — it is regenerated by
cloud-init. Add a higher-numbered file instead.

## Rollback safety

```bash
netplan try                    # apply; auto-reverts in 120s without confirmation
netplan try --timeout 30       # shorter window
```

Press Enter to accept before the timeout, or do nothing and it reverts.
**This is the only safe way to change network config on a remote host** — a
plain `netplan apply` that breaks routing to the box has no automatic
recovery short of console/IPMI access.

## Debugging

```bash
netplan --debug apply 2>&1 | tee /tmp/netplan-debug.log
journalctl -u systemd-networkd -b
networkctl status eth0
networkctl list
resolvectl status                    # DNS resolution, per-interface
ip -d link show eth0                 # driver, MTU, queueing details
```

`networkctl status <iface>` is the fastest way to see whether
`systemd-networkd` actually applied what Netplan generated — Netplan itself
has no live status beyond what it wrote to disk.
